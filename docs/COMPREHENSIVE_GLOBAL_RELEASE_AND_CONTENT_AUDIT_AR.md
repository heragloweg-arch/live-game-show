# تقرير التدقيق الشامل وخطة الإطلاق — live-game-show / قدها

## 1. الحكم التنفيذي

المصدر الحالي لتطبيق **قدها** ناضج كمرشح إطلاق تقني، ومترابط بين الواجهة ومحرك الجولة وSupabase والاقتصاد والاشتراكات والغرف والمضيفين. لا توجد حاجة الآن لإعادة بناء المشروع أو إضافة أوضاع لعب ضخمة. نقطة الاختناق الحقيقية قبل المنافسة العالمية ليست Feature جديدة، بل تشغيل بوابة الإنتاج، اختبار الأجهزة، ضبط الإيراد، وإدخال محتوى بشري نظيف.

بنك الأسئلة المرفق مفيد جدًا كرافد محتوى، لكنه **ليس بنكًا إنتاجيًا جاهزًا للظهور المباشر**. تم إدخاله إلى المشروع بطريقة آمنة كطابور مراجعة غير نشط؛ لا سؤال منه سيظهر للاعبين نتيجة هذه الدفعة وحدها.

## 2. ما تم تنفيذه في هذه الدفعة

### 2.1 دمج البنك

تمت إضافة المصدر إلى:

```text
content/question-bank/source/bank.zip
```

وتم إنشاء:

- `review-queue.json`: نسخة موحدة typed لكل الأسئلة مع الحالة والأسباب.
- `import-report.json`: إحصاءات الاستيراد.
- `20260928000041_question_bank_review_queue.sql`: Migration idempotent تُدرج المرشحين غير النشطين بحالة `needs_review`.
- `scripts/import-question-bank.mjs`: مستورد قابل لإعادة التشغيل.
- الأمر:

```bash
npm run content:import-bank
```

### 2.2 سياسة الأمان

- كل المحتوى المستورد يبدأ `active = false`.
- كل المحتوى المستورد يبدأ `qa_status = needs_review`.
- لا يتم اعتماد سؤال تلقائيًا اعتمادًا على صحة JSON فقط.
- لا تُرسل الإجابة الصحيحة للاعب؛ تبقى في `challenge_choices.is_correct` الخادمية.
- الاستيراد قابل لإعادة التشغيل دون إنشاء نسخة جديدة من نفس السؤال.
- الأسئلة المفتوحة الخاصة بالسرعة لا تدخل مسار Solo/1v1؛ تحتاج إجابة مقفلة أو `letter_pool` أو تبقى للمضيف فقط.

## 4. سياسة اعتماد المحتوى قبل الإنتاج

### الطبقة الذهبية

تُعتمد فقط بعد مراجعة بشرية سريعة إذا كانت:

- أربعة خيارات متجانسة من نفس نوع الإجابة.
- إجابة صحيحة واحدة واضحة.
- لا توجد إجابة ثانية محتملة.
- نص السؤال لا يحمل غموضًا أو ترجمة ركيكة.
- الشرح قصير ومطابق للإجابة.
- لا توجد مطالبة بحقوق أو معلومة حساسة بلا مصدر.

### الدين والقرآن والسيرة

لا تُنشر آليًا. يجب:

- مراجعة بشرية متخصصة.
- تسجيل مصدر أو مرجع داخلي للمعلومة.
- رفض الأسئلة المختلف عليها أو ذات الصياغة المطلقة غير الدقيقة.
- فصل الأسئلة الدينية في cohort مستقل قبل التفعيل العام.

### السرعة

كل سؤال سرعة بلا خيارات أو إجابة مقفلة يُحفظ `needs_review`، ولا يُستخدم في Solo أو 1v1. المسارات الآمنة له:

1. إضافة إجابة رئيسية وإجابات مقبولة.
2. توليد `letter_pool` من الإجابة مع مشتتات قليلة.
3. إبقاؤه في Host حيث الحكم البشري واضح.

## 5. طبقات المنتج والجاهزية

### المصدر والمعمارية

- جذر المستودع: `live-game-show`.
- مصدر حقيقة واحد؛ لا تعتمد ZIP قديمة كمصدر تشغيل.
- CI الحالي يغطي typecheck وlint والاختبارات والبناء وفحص الإنتاج.
- العقود الأساسية typed، والتسوية والاقتصاد server-authoritative.

### اللعب

المسارات الأساسية الموجودة يجب اختبارها تشغيليًا لا الاكتفاء بوجود الملفات:

- Solo عبر الصعوبات.
- Daily 3/3.
- 1v1 وRematch.
- Room وHost.
- Team مع timeout وreconnect.
- Shop وCosmetics.
- Plus يخفي الإعلانات.

### الأمن والاقتصاد

- لا تُفعّل مشتريات Play بلا تحقق Google Play API.
- `ALLOW_UNVERIFIED_PLAY_PURCHASES` ممنوع في الإنتاج.
- المكافآت تعتمد على ledger وعمليات ذرية.
- Creator approval reward idempotent.
- لا تستخدم multiplier الاشتراك في النقاط أو XP.
- جميع migrations تُطبق قبل فتح أي شراء حقيقي.

### الواجهة وتجربة المستخدم

- Night / Day / System موجودة كطبقة هوية حقيقية.
- الإيقاع السينمائي يجب أن يبقى هادئًا، مع حركة قابلة للتقليل.
- لا تظهر الإعلانات أثناء الإجابة.
- لا تضف وضع صور منفصلًا؛ الصورة وسيط لنفس السؤال.

## 6. الصور والأسئلة البصرية

يمكن دعم الصور دون Feature مستقلة عبر إضافة `image_url` nullable إلى `challenges`، ثم:

- عرض الصورة أعلى السؤال.
- الإبقاء على الاختيارات أو الحروف أسفلها.
- استخدام نفس answer RPC.
- تخزين WebP مضغوط في Supabase Storage.
- رفض صور الوجوه بلا إذن أو العلامات التجارية غير المرخصة.
- اعتماد الصورة والسؤال معًا في QA.

التوصية: تنفيذ هذا بعد تثبيت بوابة التشغيل، وبحزمة أولى من 50–100 سؤال بصري فقط.

## 7. TikTok

المرحلة الأولى الصحيحة ليست ادعاء تكامل عميق، بل:

1. بطاقة نتيجة سينمائية قابلة للمشاركة.
2. قالب Daily قصير: السؤال، النتيجة، الدعوة.
3. رابط من TikTok إلى Room أو Challenge.
4. Host يوجه الجمهور من اللايف إلى كود الغرفة.

أما SDK أو Login أو Ads أو بث مرتبط رسميًا فيحتاج حساب مطور TikTok وموافقات وسياسات تختلف حسب البلد. لا ينبغي تأجيل الإطلاق بسبب هذا التكامل.

## 8. بوابة الإنتاج الإلزامية

قبل أي لاعب يدفع أو ظهور إعلانات إنتاجية:

1. `supabase db push` حتى `20260928000041`.
2. نشر جميع Edge Functions.
3. ضبط Supabase production secrets.
4. ضبط AdMob production IDs و`VITE_ADMOB_TEST=false`.
5. إنشاء منتجات Play وربط Service Account.
6. تشغيل:

```bash
LAUNCH_GATE=strict npm run verify:launch-config
```

7. تنفيذ `npx cap sync android`.
8. بناء AAB موقّع بــ keystore محفوظ خارج المستودع.
9. Internal Testing في Google Play.
10. شراء وRestore على جهاز فعلي.
11. اختبار جهازين أو أكثر لـ Team/Room/Host.

## 9. القياس بعد Soft Launch

لا نعلن نجاح عالمي قبل جمع أرقام حقيقية:

- D1 وD7.
- إكمال Daily 3/3.
- نسبة بدء أول مباراة بعد التسجيل.
- نسبة Rematch.
- متوسط الجلسة وعدد الجولات.
- eCPM وARPDAU.
- تحويل Free إلى Plus.
- فشل الشراء والاستعادة.
- انقطاع Room ووقت الاستعادة.
- معدل الأسئلة المبلغ عنها.

## 10. القرار النهائي

البنك أصبح **متصلًا بالمشروع كطابور مراجعة آمن** وليس كإطلاق أعمى. هذا هو القرار الصحيح هندسيًا وتسويقيًا: نكسب حجم محتوى كبيرًا دون التضحية بثقة اللاعب.

الخطوة التالية ليست إضافة Features عشوائية؛ بل:

1. تطبيق migration في Staging.
2. مراجعة بشرية للطبقة الذهبية.
3. تفعيل cohort صغير فقط بعد QA.
4. تشغيل بوابة Play/AdMob/Supabase.
5. اختبار أجهزة وقياس Soft Launch.
6. فتح المحتوى تدريجيًا بناءً على البلاغات والأداء.

**التقييم الصادق:** الكود مرشح إنتاجي قوي، والبنك يرفع الطاقة المحتوية للمشروع بوضوح، لكن الجاهزية العالمية الفعلية لا تثبت إلا بعد التشغيل الحي والقياس والمراجعة البشرية للمحتوى.
