# Sprint 2 — تقرير أمان قاعدة البيانات

التاريخ: 18 أكتوبر 2026
المستودع: `heragloweg-arch/live-game-show`
قاعدة البيانات: مشروع Supabase الحالي (لا فرع جديد)

## التغييرات المنفذة
- أضيفت migration `20261018015606_lockdown_client_table_privileges.sql` إلى `main` لتتطابق مع رقم migration الذي سجله Supabase عند التطبيق.
- طُبقت migration على قاعدة البيانات الحالية.
- أُزيلت صلاحيات `TRUNCATE`, `TRIGGER`, و`REFERENCES` من أدوار `PUBLIC`, `anon`, و`authenticated` عن كل جداول public؛ هذه الصلاحيات لا ينبغي أن تكون متاحة لعميل التطبيق، وTRUNCATE لا تحكمه سياسات RLS.
- سُحبت صلاحية استخدام schema `private` والتنفيذ المباشر لدالة `private.is_current_user_room_member(uuid)` من أدوار العميل.
- أُضيفت تأكيدات تمنع نجاح migration إذا وُجد جدول public بلا RLS.
- أضيف ملف فحوص SQL لتأكيد الصلاحيات وRLS وsearch_path لدوال SECURITY DEFINER.

## نتيجة التحقق بعد التطبيق
- 57 جدولًا في schema public.
- RLS مفعّل على 57/57 جدولًا.
- 0 جدولًا بقيت عليه صلاحيات عميل غير آمنة من نوع TRUNCATE/TRIGGER/REFERENCES.
- anon/authenticated لا يستطيعان استخدام schema private أو تنفيذ دالة العضوية الداخلية.
- 0 دوال SECURITY DEFINER في public/private بلا search_path مثبت.
- migration مسجلة في سجل Supabase بالنسخة `20261018015606`.

## ما لم يُغلق بعد
- 16 جدولًا عليها RLS بلا سياسات؛ هذا يمنع الوصول عبر RLS افتراضيًا، لكن يجب مراجعة ما إذا كانت كل حالة مقصودة وتوثيقها.
- سياسات SELECT الممنوحة لدور public/anon في بعض الجداول، وخصوصًا سياسة قراءة `profiles` العامة التي قد تكشف أعمدة الاقتصاد والاشتراك؛ يلزم حسم عقد بيانات الملف العام قبل تعديلها حتى لا تنكسر واجهات المستخدم.
- لا تزال اختبارات التكامل بحسابات مستخدمين حقيقيين مطلوبة، بما فيها المالك/غير المالك والمستخدم المحظور والمشرف.
- لا يعني نجاح فحوص SQL أن Sprint 2 مغلق بالكامل؛ يلزم تدقيق سياسة الملف العام وتغطية السياسات لكل جدول.
